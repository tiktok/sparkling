# Working on Sparkling

This file is for coding agents working **on this repository**. For an agent
working on an app *built* with Sparkling, the equivalent file ships in the
template: `template/sparkling-app-template/AGENTS.md`.

Read [CONTRIBUTING.md](./CONTRIBUTING.md) for the commit format - it is enforced
by review - and [AGENT_E2E_UI_TESTING.md](./AGENT_E2E_UI_TESTING.md) for the
end-to-end run that any change to the CLI, template, SDK or Method system needs
before it is proposed.

## What lives where

| Package | What it is |
| --- | --- |
| `packages/sparkling-sdk` | The containers. `android/` is Kotlin, `ios/` is Swift. Scheme parsing, lifecycle, navigation, the debug tag. |
| `packages/sparkling-method` | The Method runtime: the pipe, the registry, the platform data processors. |
| `packages/sparkling-method-cli` | `init` and `codegen` for a Method package. TypeScript. |
| `packages/sparkling-app-cli` | `build`, `dev`, `autolink`, `run:*`, `doctor`. Owns `app.config.ts` and all native-project surgery. |
| `packages/create-sparkling-app` | Scaffolds an app from `template/`. |
| `packages/methods` | The shipped ability packages: storage, media, navigation. |
| `packages/playground` | The demo app, and the host for the Android and iOS unit tests. |
| `template/sparkling-app-template` | What every new app starts as. |

## Building and testing

```bash
pnpm install                                   # once, at the root
pnpm --filter <package> test                   # TypeScript packages (jest)
bash scripts/coverage-android.sh               # Android unit tests, from packages/playground/android
```

- The **Android** unit tests run through the playground's Gradle project
  (`./gradlew :sparkling:testDebugUnitTest`) and CI pins **JDK 17**. Newer JDKs
  fail the `JdkImageTransform` for `compileSdk 34`, so a machine with only JDK 21
  cannot run them - say so in the PR rather than claiming they passed.
- The **iOS** unit tests run from the playground workspace on macOS.
- `.github/workflows/ci.yml` decides what runs from the paths you touched.

## Things that are not guessable from the source

**`module.config.json` is read by two tools with different keys.**
`sparkling-method-cli` reads `packageName` and `moduleName`.
`sparkling autolink` reads `name`, `methods`, `android.packageName`,
`android.className` and the `ios` block. A file with only one set produces a
module that links and registers nothing. Both sets belong in the file.

**Codegen emits abstract classes only.** `kotlin-impl-template`,
`swift-impl-template`, `oc-idl-template`, `oc-impl-template` and `ts/call-template`
are empty files that no code reads. The concrete `<Module><Method>Method` class
is written by hand; autolink registers *that*, not the generated `Abs…MethodIDL`.

**The shipped method packages were not produced by the CLI.** Their headers say
`GENERATED BY ANYCODE`, and their layout is the convention the rest of the
toolchain assumes: package `<android.packageName>.<methodName>`, abstract
`Abs<Module><Method>MethodIDL`, concrete `<Module><Method>Method`. Match it.

**Autolink is text surgery.** It rewrites `settings.gradle(.kts)`,
`app/build.gradle(.kts)` and the `Podfile` and generates two registries. It has
no notion of a native library, CMake, or a Lynx library - `lynx.lib.json` is
handled by `lynx-library-plugin` / `cocoapods-lynx-library`, which are separate.

**The two containers disagree in places.** iOS decides what a scheme URL means
from its host and query alone; Android also checks the scheme prefix. iOS lays a
page out below the status bar and paints that strip itself; Android lays out
below it. When you change one container, check whether the other needs the same
change, and say in the PR which platforms you verified.

**Scheme flags compare against the string `"1"`.** `SchemeConstants.Value.ENABLED`.
Anything else - `true`, `yes` - is false.

**The debug tag is drawn by the SDK.** `SparklingView.addDebugTagView()` paints
it whenever the app is debuggable and a debug tool provider is on the classpath.

## Conventions

- Commit titles are `[Label] Title` with `[Feature]`, `[BugFix]`, `[Refactor]`,
  `[Optimize]`, `[Infra]`, `[Testing]` or `[Doc]`, plus a structured summary.
  Add a platform label where it helps: `[BugFix][Android]`.
- One problem per PR, one package where possible.
- Docs are bilingual: a change under `docs/en/` usually needs the same change
  under `docs/zh/`.
- Generated output is not committed: `dist/`, copied `.lynx.bundle` files,
  native build directories.
- New behaviour comes with a test in the package that owns it. A bug fix comes
  with the test that would have caught it.

## Reporting

State what you ran and what it said. If a platform's tests could not run here,
name the reason. "Should work" is not a test result.
